1563. Stone Game V
Problem

You are given an array stoneValue representing stones arranged in a row.

Alice repeatedly:

Splits the current row into two non-empty parts.
Let:
leftSum = sum of the left part
rightSum = sum of the right part
Bob removes the part with the larger sum.
Alice gains the sum of the part that remains.
If both sums are equal, Alice can choose either part to keep.
The game continues until only one stone remains.

Return the maximum score Alice can obtain.

Example
stoneValue = [6,2,3,4,5,5]

One optimal strategy:

[6,2,3] | [4,5,5]
   11   |   14

Bob removes the right side because 14 > 11.

Alice gains:

11

Remaining:

[6,2,3]

Split:

[6] | [2,3]
 6   |  5

Bob removes [6].

Alice gains:

5

Remaining:

[2,3]

Split:

[2] | [3]
 2   |  3

Bob removes [3].

Alice gains:

2

Total:

11 + 5 + 2 = 18

Therefore:

Output = 18
1. Important Observation

This is a Dynamic Programming on Intervals problem.

Why?

At any point, Alice is working with a continuous subarray:

stoneValue[l ... r]

She chooses some partition point k:

[l ... k] | [k+1 ... r]

After Bob removes one side, the next game is played only on the remaining interval.

So our state can be:

dp[l][r]

meaning:

Maximum score Alice can obtain from the subarray stoneValue[l...r].

2. What happens at a partition?

Suppose:

stoneValue[l ... k] | stoneValue[k+1 ... r]

Let:

leftSum  = sum(l ... k)
rightSum = sum(k+1 ... r)

There are three cases.

Case 1: leftSum > rightSum

Bob removes the left part.

So Alice keeps the right part.

Alice gets:

rightSum

and the game continues on:

[k+1 ... r]

Therefore:

rightSum + dp[k+1][r]
Case 2: leftSum < rightSum

Bob removes the right part.

Alice keeps the left part.

Alice gets:

leftSum

and the game continues on:

[l ... k]

Therefore:

leftSum + dp[l][k]
Case 3: leftSum == rightSum

Alice can choose which side to keep.

Therefore:

leftSum + max(
    dp[l][k],
    dp[k+1][r]
)
3. Recurrence

Therefore:

dp[l][r] = maximum over all k

of:

if leftSum > rightSum:
    rightSum + dp[k+1][r]


if leftSum < rightSum:
    leftSum + dp[l][k]


if leftSum == rightSum:
    leftSum + max(dp[l][k], dp[k+1][r])
4. Base Case

If there is only one stone:

l == r

Alice cannot split it.

So she cannot gain any score:

dp[l][r] = 0;
5. Why Do We Need Prefix Sum?

In your brute-force solution, you calculate the sums like this:

int lsum = 0;


for(int i = l; i <= k; i++){
    lsum += a[i];
}

and similarly for the right side.

That takes O(n) every time we calculate a sum.

We can do better using a prefix sum array.

Define:

prefix[i] = sum of elements from 0 to i-1

For example:

a = [6,2,3,4,5,5]


prefix:
[0,6,8,11,15,20,25]

Then:

Sum from l to k
prefix[k+1] - prefix[l]
Sum from k+1 to r
prefix[r+1] - prefix[k+1]

Both become O(1).

6. Why Memoization?

Without DP, the same interval can be calculated many times.

For example:

recur(0,5)

may call:

recur(0,2)

and another partition can also call:

recur(0,2)

Instead of calculating it repeatedly, store:

dp[l][r]

Then:

if(dp[l][r] != -1)
    return dp[l][r];

This converts the brute-force recursion into top-down DP / memoization.

8. Top-Down DP Code
class Solution {


            // Sum of right part
            int rsum = prefix[r + 1] - prefix[k + 1];


            if (lsum > rsum) {


                // Bob removes left
                // Alice keeps right
                ans = Math.max(
                    ans,
                    rsum + recur(k + 1, r)
                );


            } else if (lsum < rsum) {


                // Bob removes right
                // Alice keeps left
                ans = Math.max(
                    ans,
                    lsum + recur(l, k)
                );


            } else {


                // Equal sums
                // Alice chooses the better side
                ans = Math.max(
                    ans,
                    lsum + Math.max(
                        recur(l, k),
                        recur(k + 1, r)
                    )
                );
            }
        }


        return dp[l][r] = ans;
    }


    public int stoneGameV(int[] stoneValue) {


        int n = stoneValue.length;


        dp = new int[n][n];
        prefix = new int[n + 1];


        // Prefix sum
        for (int i = 0; i < n; i++) {
            prefix[i + 1] =
                prefix[i] + stoneValue[i];
        }


        // Mark all states as uncomputed
        for (int[] row : dp) {
            Arrays.fill(row, -1);
        }


        return recur(0, n - 1);
    }
}

10. Brute Force vs DP
Brute Force

Your first solution repeatedly calculates:

for(int i=l;i<=k;i++)
    lsum += a[i];


for(int i=k+1;i<=r;i++)
    rsum += a[i];

So calculating sums itself takes O(n).

And the recursion recalculates the same intervals many times.

Therefore it becomes very expensive.

Optimized DP

We use:

Prefix Sum → calculate interval sums in O(1)
Memoization → calculate each interval only once

This is the key optimization.

11. Complexity

There are:

O(n²)

possible intervals [l,r].

For each interval, we try every possible partition k.

That takes:

O(n)

Therefore:

Time Complexity
O(n³)
Space Complexity
O(n²)

for the DP table.

The prefix array requires:

O(n)

additional space.

So overall:

Time:  O(n³)
Space: O(n²)
12. Pattern to Remember

This problem is a classic Interval DP pattern.

Whenever you see:

Choose a partition point k
        ↓
left part | right part
        ↓
one/both parts continue recursively

think:

dp[l][r]

and try every:

k = l ... r-1

The general structure is:

for(int k = l; k < r; k++) {


    // calculate left and right


    // decide which interval survives


    // combine current score + future DP
}

For Stone Game V, the crucial game rule is:

Bob removes the side with the larger sum, so Alice gains the smaller sum and continues with that smaller side.
